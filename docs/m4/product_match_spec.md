# M4 Product Matching Specification

**Owner:** Hayat
**Module:** Product Matching Specification
**Schema:** `configs/m4/product_match_spec_v1.json`
**Specification Version:** `1.0.0`
**Status:** Provisional
**Milestone:** M4 – Personalization, Context, and Wardrobe Optimization

---

## 1. Purpose

The Product Matching Specification defines a versioned output contract for wardrobe-gap candidates generated by M4 Wardrobe Gap Analysis.

Its purpose is to provide structured information that a future product-matching component can use to identify products relevant to missing or underrepresented wardrobe categories.

The specification connects existing gap-analysis results with relevant item attributes, compatibility information, and optional Wardrobe Utility Score (WUS) evidence.

It defines the expected data structure without implementing marketplace integration or an actual product-matching algorithm.

## 2. Input and Output Sources

The specification uses outputs from the following M4 components:

| Component | Owner | Relevant output |
|---|---|---|
| Wardrobe Gap Analysis | Omar | Ranked gap candidates and product-matching records |
| Wardrobe Utility Score | Hana | Utility evidence and WUS components |
| Product Matching Specification | Hayat | Versioned product-matching output contract |

The specification also references selected fields from the M2 item representation for candidate attributes. It does not replace or reproduce the complete M2 item representation contract.

## 3. Product-Matching Record Structure

Each product-matching record follows the identifier:

`wardiq.m4.gap-candidate-product-record.v1`

The specification itself uses version `1.0.0`. These are separate identifiers: the former identifies the record contract, while the latter identifies this specification version.

The record contains the following required fields:

| Field | Type | Description |
|---|---|---|
| `schema_version` | string | Product-matching record schema identifier |
| `wardrobe_ref` | string | Reference to the baseline wardrobe |
| `config_ref` | string | Gap-analysis configuration reference |
| `rank` | integer | Candidate ranking position |
| `candidate_item_id` | string | Stable candidate identifier |
| `target_category` | string | Target clothing category |
| `is_synthetic_candidate` | boolean | Indicates whether the candidate was generated synthetically |
| `gap_score` | number | Gap-analysis ranking score |
| `incremental_useful_combinations` | integer | Number of additional useful combinations |
| `avg_ocs` | number or null | Average Outfit Compatibility Score |
| `unlocked_templates` | array of strings | Templates unlocked by the candidate |
| `redundancy_score` | number | Redundancy score between 0 and 1 |
| `explanation` | string | Explanation of the candidate's utility |

## 4. Optional Information

### 4.1 Candidate Attributes

The optional `candidate_attributes` object references selected information from the M2 item representation.

It may contain:

- `attributes`: attribute vocabulary source, version, scores, and missing-value mask.
- `color`: color extraction model, version, and CIELAB palette.
- `embedding`: embedding model, version, dimension, provisional-dimension indicator, and vector.
- `formality`: formality information.
- `season`: season information.

These fields represent selected attributes rather than a complete M2 item record.

Missing information must remain null or unavailable where permitted by the schema. Attributes must not be fabricated.

### 4.2 Applicable Constraints

The optional `applicable_constraints` field contains references to relevant constraints defined in the M4 Wardrobe Gap Analysis configuration.

The referenced constraints include:

| Configuration reference | Meaning |
|---|---|
| `usefulness_policy.min_useful_ocs` | Minimum OCS threshold for useful combinations |
| `usefulness_policy.count_only_structurally_valid` | Whether only structurally valid combinations are counted |
| `redundancy_policy.embedding_similarity_threshold` | Threshold for detecting embedding similarity |
| `redundancy_policy.attribute_overlap_threshold` | Threshold for detecting attribute overlap |
| `redundancy_policy.max_category_saturation` | Maximum category saturation threshold |
| `redundancy_policy.flag_exact_item_id_match` | Whether exact item ID matches are flagged |

The values are maintained in `configs/m4/gap_analysis_v1.json` and can be retrieved using the record's `config_ref`.

These references describe existing wardrobe-gap and compatibility constraints. They do not represent product-specific requirements such as size, brand, or price, which are not currently generated by the gap-analysis implementation.

The field is optional because the current producer does not populate it directly.

### 4.3 WUS Evidence

The optional `wus_evidence` object follows the existing contract:

`wardiq.wardrobe-utility.v1`

It contains:

- `schema_version`
- `wardrobe_ref`
- `candidate_item_id`
- `gain`
- `avg_ocs`
- `preference`
- `context`
- `redundancy`
- `wus`
- `config_ref`

Preference, context, and WUS values may remain null when they have not been calculated.

**Output structure clarification:** The current gap-analysis implementation returns product-matching records and WUS handoff records as separate outputs (`product_matching_records` and `wus_handoff`). The optional `wus_evidence` object in this specification describes a nested representation for downstream use; it does not mean that the current implementation already nests WUS records inside product-matching records.

### 4.4 Future Catalog-Matching Information

The optional `catalog_matching` object reserves fields for a future application layer:

- `product_id`
- `brand`
- `size`
- `price`
- `currency`
- `product_url`

These fields do not indicate that catalog integration has been implemented.

## 5. Validation Rules

The specification uses JSON Schema Draft 2020-12.

The main validation rules are:

1. All required product-matching fields must be present.
2. Required candidate identifiers and references must be non-empty strings.
3. Candidate categories must belong to the category vocabulary defined in the schema.
4. Rank must be a positive integer.
5. Incremental useful combinations must be a non-negative integer.
6. Redundancy scores must be between 0 and 1, inclusive.
7. Attribute scores, when available, must be between 0 and 1, inclusive.
8. Color palette values must follow the specified CIELAB ranges: L from 0 to 100, and a and b from -128 to 127. Palette proportions must be between 0 and 1, inclusive.
9. Missing values must be represented using null where permitted by the schema.
10. Undefined additional properties are rejected in the defined objects.

The WUS evidence object must follow the existing `WardrobeUtility` handoff structure.

These examples demonstrate the existing output structure and missing-value policy. The WUS record is shown separately because that is how the current implementation returns it.

## 7. Traceability

Product-matching records must preserve the references needed to identify their original gap-analysis results.

The following relationships must remain consistent:

| Reference | Purpose |
|---|---|
| `candidate_item_id` | Identifies the same candidate in product-matching and WUS outputs |
| `wardrobe_ref` | Identifies the baseline wardrobe |
| `config_ref` | Identifies the configuration used to generate the gap-analysis result |
| `schema_version` | Identifies the output record contract |

Candidate identifiers must not be regenerated during downstream processing.

## 8. Assumptions and Limitations

- Product matching is represented as a versioned output contract only.
- No marketplace or live catalog integration is implemented.
- Candidate attributes depend on the availability of M2 item representations.
- The candidate attributes object contains selected M2 fields, not the complete M2 record.
- WUS values depend on Hana's calculation and are not fabricated.
- Preference and context values may remain unavailable.
- Average OCS may be null when compatibility embeddings are unavailable.
- Synthetic candidates represent missing wardrobe categories, not actual purchasable products.
- Catalog-matching fields are reserved for future integration.
- The specification remains provisional pending integration review.

## 9. Versioning

The specification currently uses version `1.0.0`.

Changes to the record structure must be reflected in the schema version and reviewed by downstream consumers.

Breaking changes require a new major version and downstream revalidation.

The current status is provisional pending integration review.
